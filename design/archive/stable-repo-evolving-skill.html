How the skill keeps improving without breaking anyone's repo

The problem, from first principles: our bug-finding brain will keep changing, but pieces of it live as files inside users' repositories. Here is how we draw the line so that our churn never becomes their refactor.

Part 2 of 2 — the product (the contract, lifecycle, pages, and operating model). Companion: ⚗️ Scenarios from atoms — the method: how the engine generates and searches. Read that one first.

1Background: what the system actually is

The workload harness is two things that live in two different places:

  • The skill — the searching brain. It reads a product's docs and code, decides which situations to test, generates the tests, runs them, and judges the results. We ship it, we version it, and we will keep rewriting it as we learn what finds bugs.
  • The .workers/ folder — the skill's working state, checked into the user's repository. Flow definitions, coverage bookkeeping, generated scenarios, findings.

Four search strategies in six weeks — on our own lanes, that churn was a branch. After launch, the same churn would land inside customer repositories.

Here's the uncomfortable fact this design has to absorb: the search strategy is not done. We have rewritten it four times in six weeks, and each rewrite so far also reshaped the folder — different file types, different frontmatter fields, different names for things. Internally that cost nothing: each experiment ran on a fresh branch. But the moment real users have .workers/ folders, "we reorganized the taxonomy" means asking every customer to refactor files they didn't write and don't fully understand. That is the thing we must make impossible.

The question, precisely

How do we keep a stable structure in the user's repo while remaining free to change the skill's taxonomy and search approach underneath it?

2Intuition: four old principles, applied

Nothing here requires a new idea. Software has solved this exact problem several times — we just have to notice which files in .workers/ map to which side of each classic boundary.

Principle 1 — Source vs. build output: never make users edit what a machine produced

Toy example. A C compiler changes its optimizer every release. Object files (.o) come out completely different — different layout, different symbols. Nobody cares, because nobody hand-edits object files: you keep the source, you re-run the compiler. Same with node_modules/, lockfiles, or a build cache — machine-owned things get regenerated, never migrated by hand.

Applied. Most of today's .workers/ content — coverage tables, scenario files, the search's bookkeeping — is build output of the skill. It only feels like precious hand-maintained state because early versions asked people (and agents) to author it directly. Once it's formally "compiled from a small source by the skill," we can change its shape every single release: delete the folder, regenerate, done. Churn is free wherever the machine owns the file.

Principle 2 — Interface vs. implementation: the user touches a small, frozen surface

Toy example. pytest users write one thing: functions named test_*. That interface has held for ~15 years while pytest internally rewrote test collection, ordering, fixtures, and plugins many times over. Users never renamed a file for pytest's benefit. Counter-example: imagine a test framework that required you to arrange tests into folders named after its current strategy — unit/, integration/, corridors/… Every strategy rethink would ripple into every user's tree. That framework would be trapped: unable to improve without hurting its own customers.

Applied. The user-facing surface must contain only facts about the user's product — what it promises, what a "job" or "queue" means, what counts as broken. Those facts change when their product changes, not when our strategy changes. Everything that encodes how we search — priorities, orderings, taxonomies of attack — stays behind the interface, where we can rewrite it freely.

Principle 3 — Your own observation: code is stable, metadata is fragile

You said it exactly right, and here is why it's true. A workload written as code is validated by execution: its contract is the product's real API. client.enqueue(task) either runs against DBOS or it doesn't — and the product's API is the thing its vendor already keeps stable for their own users. Frontmatter, filenames, and folder placement are validated only by convention: their contract is "whatever the current version of our skill expects to read." When we change the skill, code keeps working; conventions silently rot.

Applied — three concrete rules.

  • Prefer code over declaration. Push as much of the user-facing surface as possible into runnable code (the flow's setup, operations, checks). If a fact can be derived by inspecting the code, don't ask for it in frontmatter at all.
  • Whatever must be declared, treat like a database schema: a named, versioned set of fields that only ever grows — new fields arrive with defaults, old fields keep meaning. (This is protobuf's rule, and Rails migrations' rule. Boring on purpose.)
  • Address by key, never by path. The skill refers to a flow as enqueue-and-complete (a key inside the file), not as flows/queue/enqueue.yaml (a location). Then filenames and folder arrangement belong to the user's taste, and nothing we ship can ever be broken by — or ever demand — a rename.
Principle 4 — When the frozen surface must grow: migration is a command, and we drafted the files anyway

Toy example. Django apps evolve their database schema for years without anyone re-typing their data: manage.py migrate replays small, reviewed, additive changes. The schema moves; the data survives; the human's job is to review, not to retype.

Applied. Rarely, a genuine improvement needs a new declared fact (say, flows must now name their checkpoints). Then wio migrate runs — and here our product has an unfair advantage over Django: the agent drafted these files in the first place, from the user's own docs and code. So the migration isn't even "user fills in the new field" — it's "agent re-derives the new field, user reviews a diff." The user's unit of work stays constant forever: read a short diff and say yes or no. Never author, never refactor.

3The design, concretely: three zones in one folder

Put the four principles together and .workers/ divides into three zones with different ownership and different change rules:

Product truthuser-ratified · frozen interface
A small set of flow atoms: mostly runnable code (how to enqueue a task, how to check it completed) plus a minimal declared block (what this flow promises, which invariants must hold). Facts about their product. Drafted by the agent, ratified by the user. Changes only when the product changes. model/flows/enqueue_and_complete.py  ·  model/resources.py
Search statemachine-owned · regenerable
Everything encoding how we currently search: which situations exist, what's covered, what's owed, generated scenarios, priority views. Compiled by the skill from the product truth. Deletable and rebuildable at any time — so its shape can change with every skill release, invisibly. generated/scenarios/  ·  generated/coverage/  ·  generated/debt/
Evidenceappend-only · immutable
Confirmed findings and run records, each stamped with the exact model and skill version that produced it. Never regenerated, never migrated — history stays readable under the version that wrote it. evidence/findings/  ·  evidence/runs/
Ownership decides change rules. Green = user's, stable, tiny. Amber = ours, churns freely, regenerated. Grey = history, frozen forever.

A flow atom, to make "mostly code, minimal declaration" tangible — one file, declarations living in the code so nothing can drift (a YAML projection is generated from it for review, never authored; the full anatomy — every field's job, the resource classes, the type-derivation — is ⚗️ §3):

# enqueue_and_complete.py — ONE file; no sidecar metadata to fall out of sync
@flow(
    key="enqueue-and-complete",      # ← the skill addresses THIS, never the file path
    invariants=(EXACTLY_ONCE, ACK_NOT_LOST),  # promises — what the user ratifies
    resources=(QUEUE_STATE, EXECUTOR_OWNERSHIP),
)
def enqueue_and_complete(ctx, queue: Queue, task: Task) -> Result:
    # inputs/outputs derived from the typed signature; validated by the product's own API
    wf = ctx.client.enqueue(queue, task)
    return ctx.await_result(wf)

Notice what disappeared from the table: there is no row where the user reorganizes files, renames anything, or authors content. The worst case in the whole design is "read a short diff." And the two amber rows should be rare precisely because Principle 3 keeps the declared surface tiny — most of what we'll want to change lives where changing it costs nothing.

But wait — if the search record is regenerable, how do we know how much we've searched?

This is the sharpest question in the whole design, and it exposes a distinction hidden inside "search state." The amber zone is really two things, and only one of them is regenerable:

  • The map — which situations exist, which are valid, what's owed, what should run next. This is a pure function of the green model plus the skill's current policy (generation is required to be deterministic from model-version + policy + seed). Regenerating it is just re-running a compiler; nothing in it was ever information you could lose.
  • What actually ran — this is never stored in amber as truth. Every run and every finding is appended to the evidence ledger (the grey zone): immutable, each record stamped with its full semantic coordinate (flow, modality, event, seed, fault timing) and the exact model and skill versions that produced it.
The ledger and the balance

"How much have we searched?" is answered by recomputation, never by a stored file: coverage = evidence ledger ⨯ current map. It's a bank account — the ledger is the transactions (grey, append-only), the balance is a derived view (amber). You can delete the balance file any time, because the ledger regenerates it. That is exactly why amber is safe to reshape every release.

The interesting case is a taxonomy change. What happens to coverage:

  1. Old evidence keeps its original coordinates forever — it's immutable and version-stamped.
  2. The new compiler maps old records into new cells wherever the mapping is deterministic; those cells count as covered.
  3. Cells the old slicing never distinguished honestly show as unsearched. That's deliberate, not a loss — the migration rule is "no false explicit coverage." If the new taxonomy splits a situation the old one lumped together, we genuinely don't know both halves were covered; claiming otherwise would be the lie. We re-search them, and deterministic seeds make replaying old scenarios into new cells cheap.

So a taxonomy change never loses what we did (the ledger is untouched) — it can only shrink what we're allowed to claim. And that shrink is precisely the reason we wanted the new taxonomy in the first place.

Who drafts a migration — deterministic code or the agent?

Both, chosen by the kind of change:

  • Mechanical changes → deterministic code. Rename a field, add a field with a constant default, restructure the YAML shape. Literally the Rails/Django pattern: a small versioned script, testable, replaying identically on every repo. No model involved.
  • Semantic changes → the agent drafts, because deterministic code can't. If flows must now declare checkpoints:, no script can know where your product's meaningful checkpoints are. But the agent derived the original flow atoms from the user's docs and code — so it re-derives the new field the same way, and its output is never applied directly: it's a diff the user approves.

Both tiers funnel into the same human motion — review a diff. A change that fits neither tier makes wio migrate hard-fail with a message saying what's needed; it never silently guesses.

How we know the line is drawn right before launch

The boundary is a claim, so it gets a test. Before the schema is declared public: run one full internal search-strategy overhaul — swap the taxonomy, swap the ranking — and check that git diff on the user-ratified zone is empty. If any strategy change forces an edit to a green-zone file, the boundary is in the wrong place and we move it before customers exist, while moving it is still just a branch.

The contract, in one sentence each

Green zone: yours; tiny; mostly code; we address it by key, never by path; its schema only grows, never breaks.
Amber zone: ours; regenerable; its shape is not a promise and may change every release.
Evidence: frozen; every artifact stamped with the versions that made it; always readable.
Migrations: deterministic scripts where mechanical, agent-drafted diffs where semantic, human review in both — never a human that refactors.

4The user flow: who runs what, and when a red counts

Three questions decide the whole user experience: where does search run (and who pays for it), when does a failing workload deserve to be visible, and what does the board show for everything that didn't run. Each has a clean answer once you see one distinction.

Search and replay are different activities with different costs

Search is the agent thinking: reading the product, inventing scenarios, deciding where to aim. It costs tokens and takes hours. Replay is executing a scenario that already exists — pinned seed, pinned schedule, pinned fault timing. It's deterministic, costs only compute, needs no model at all, and takes minutes. A found scenario is a compiled asset: expensive to discover, nearly free to re-run forever. That one fact places everything:

Local, while building
developer's machine · on demand
  • Search tokens — agent drafts new flows & scenarios for the feature
  • Replay no tokens — iterate a draft until control is green and red-proof passes
  • Everything here is draft: visible to you, never on the team board
Continuous, on main
scheduled · budgeted
  • Deep search tokens — the harness keeps hunting new situations against main
  • Promotes scenarios that pass the gates to official
  • Maintains the baseline: last full assessment at a known SHA
CI, on every PR
minutes · gate
  • Replay only no tokens — no searching in CI
  • Impact-selected: re-run official scenarios whose flows touch changed surfaces
  • Verdict = diff vs baseline; everything untouched inherits baseline state
CI never searches — it replays compiled assets against the new commit, which is why it fits in minutes and costs no tokens. The expensive thinking happens locally (scoped to your feature) and continuously on main (budgeted, deep).

You want reds while building — a workload that has never failed proves nothing (that's what the red-proof is). The question is never "may it fail?" but "who sees it?" The gate is on publication, not execution:

Promotion gates (already proven in our own lanes): the control must pass (the simple version of the situation works — so the workload isn't just broken), the red-proof must pass (the oracle demonstrably can fail — so green means something), and a reviewer keeps it. A draft red that survives all three isn't noise to hide — it's either a finding or the feature isn't done, and the author knows which.

This answers the half-built-feature case directly: declare the flow, let the agent draft scenarios, run them red all day — the board shows nothing until you promote. TDD ergonomics: red locally is progress; red on the team board is a promise broken. And "should we allow it?" — yes, always allow running; gate publishing. A tool that refuses to run incomplete things gets abandoned.

Partial runs: what the board shows for everything that didn't run

A PR run replays maybe six scenarios out of hundreds. The board never goes blank for the rest — every cell shows its last official assessment with its age. Coverage state carries forward until superseded, exactly like the ledger implies (the balance doesn't reset because today had only two transactions):

So the status page is never "the result of the last run." It is the current best knowledge per promise — freshest evidence wins per cell, staleness visible, debt visible, drafts invisible. One ledger; the PR view, the builder's view, and the release view are just three filters over these same cells.

5The pages: seven views, two worlds

The UI skeleton every mature test product converges on — a home board on the default branch, a diff page per PR, a detail page with history per test/issue, an explorer — maps directly onto our objects. Seven pages cover every moment; everything else is a filter, not a page.

  • Same pages, scoped to your working tree

One rule, no sharing model to invent: a ref on origin gets a team page, local-only work gets a personal one. Promotion (draft→official) and publication (personal→team) are the same motion seen from two sides — which is why a half-built workload's reds structurally cannot leak onto a team page.

Why the default view leads with promises when scenarios are the unit

To be precise about what the home page is not: it is not "the" board — the plan mandates twelve projections from one ledger (by dimension, by mechanism, by frontier, by debt floor…), and none is canonical. The home page is just the projection chosen as the default landing, and it leads with promises (a flow-grouped promise list, with per-dimension coverage chips carrying the search dimensions) for the reasons below. The choice is a reversible product bet: every view is a cheap GROUP BY, so if real users' first question turns out to be "where is it searching" rather than "do my promises hold," flipping the landing is one route change, zero migration.

Because the object counts diverge over time, and only one layer stays human-scale. Flows × invariants is tens of rows and grows only when the product grows. Scenarios are thousands and grow forever — compositional generation never stops manufacturing them. Runs are millions. The reading order is a pyramid:

The aggregation pyramid

Promises (tens — the board) ← situations (hundreds — the lattice, page 5) ← scenarios (thousands — the explorer, page 4) ← runs (millions — the ledger). Humans read the top; every level is one click down. Severity attaches to invariant classes, so the top layer is also the only place a severity-weighted posture can be expressed.

Two honesty rules make the coarse index safe: a cell is never a bare checkmark — its verdict (worst-of its scenarios) always ships with its depth ("holding · 34/61 situations searched"), so aggregation can't lie about how hard the promise was attacked. And composed scenarios credit every flow coordinate they carry, with interaction coverage getting its own projection — the flow × flow coupling matrix on page 5, which shows which state-sharing pairs have never been attacked together. The grid is a GROUP BY over coordinates, not the storage; it handles many-to-many composition natively.

7Check your understanding

Six questions, medium difficulty. Click an answer to see the reasoning.

Question 0
A developer is building a workload for a feature that's only half-implemented, and it fails on every local run. What does the rest of the team see on the promise board?
The gate is on publication, not execution: draft runs stay in the developer's workspace, and the board only ever reflects official scenarios. Existing cells are untouched (their last-known state carries forward), and the draft appears at most as an off-board "◐ draft in progress" note — never as a red. Reds earn board visibility only after control-green, red-proof, and review promote the scenario.
Question 1
We ship skill v3.4, which completely replaces how scenarios are prioritized and renames every internal coverage category. What happens in a customer's repo?
Prioritization and search taxonomy are search state — build output. The skill deletes and regenerates that zone on its own; migration and review are reserved for the rare case where the declared user-facing schema grows. (History lives in the evidence zone, not by preserving stale build output.)
Question 2
Why is a flow written as runnable code more durable across skill versions than the same information written as frontmatter metadata?
Execution validates code against something outside our control that is already kept stable — the product's real API. Conventions (field names, folder meanings) are validated only by our own reader, which is exactly the thing we keep changing. Key-addressing is true but applies to both code and metadata; the zone placements in the other options are wrong.
Question 3
A real improvement needs flows to declare something new — say, named checkpoints where faults can be injected. What is the designed path?
The schema is frozen against breaking, not against growing. Additive field + default + agent-drafted values + human review keeps the user's unit of work at "read a diff." Making users author it violates agent-drafts-user-ratifies; reading all formats forever piles up complexity that eventually breaks anyway; and pure runtime inference is right only when it's reliable — when it isn't, the fact belongs in the reviewed declaration.
Question 4
Which change would prove the compatibility boundary was drawn in the wrong place?
The invariant is: search-strategy changes never require edits to user-ratified files. A strategy that reaches into the green zone means strategy concerns leaked into the frozen interface — the boundary must move. The other three are the design working exactly as intended: regenerable build output, immutable stamped evidence, key-over-path addressing.
Question 5
Before declaring the schema public at launch, what is the concrete rehearsal that tests the whole design?
The design's promise is "our churn is never your refactor" — so the rehearsal is to cause the churn on purpose (swap taxonomy, swap ranking) and mechanically check the promise: zero diff in the green zone. Scaffolding, determinism, and hand-authoring tests are all useful, but none of them exercises the one claim the whole boundary exists to make.
