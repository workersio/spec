Scenarios from atoms: the compositional approach, and the skill that can experiment its way there

How generating tests from a small algebra of trusted parts solves the aiming problem that scoring never could — and the structural rethink that lets the skill get there by experiment instead of by rewrite.

The why of the set — the method and its arguments. Companion: 🏛 The product book — the machine and the experience that wrap this engine (pieces, run trace, repo zones, lifecycle, the pages, who does what). Read this one first.

The whole argument, one screen

1 · Eight measured runs say the harness maps and verifies but doesn't aim — and scoring can't fix aiming, because a score only reorders a list that never contained the missing situations (§1).
2 · So stop authoring situations: author ~a dozen trusted flow atoms and let a typed algebra generate every valid combination — a generated scenario is an aim (§2–4).
3 · Because the space is enumerable, "never tried" becomes countable debt that gates the search; attention is demoted to tie-breaker; the only honest stops are budget-exhausted or zero-debt (§5).
4 · Atoms are code in the product's own language — declarations live in the code, so nothing drifts — and one engine speaks to every language through a frozen manifest/observation protocol (§3, §6).
5 · The skill splits into engine (tested code) / policy (versioned data) / judgment (the agent), so improving the method becomes a cheap, attributable experiment up a cost ladder — never a rewrite (§8).
6 · Path: ratify §24 → smallest prototype → one treatment at a time → blind rows → promote (§7 has the pointer; the plan of record is the decision packet).

1Background: why generation, not better scoring

Vocabulary: two L-scales that share letters — don't conflate them

The interception funnel (L1–L4) — the four stages a real bug must survive, in order, for the harness to catch it. This is how every lab row is graded, and where the 94% / 9% / 58% numbers below live:

L1 · Map — is the bug's surface/seam represented in the model at all? (~94% — solved)
L2 · Aim — did any scenario actually attack the bug's specific situation? (9%, pinned four rows — the wall this whole design attacks)
L3 · Oracle — if the failure fired, would an oracle notice? (~58% — improving)
L4 · Catch — did a run actually go red and get confirmed? (0% — the product of the three above)

Scenario rungs (L0–L4) — an unrelated scale describing one scenario's complexity: L0 attributable control · L1 one adversarial dimension · L2 interaction between actors/flows · L3 an event/state landing mid-attack · L4 scale/soak. Rule of thumb: percentages and "the wall" = funnel; a label on a single scenario = rung. (Coincidentally, the bugs we keep missing are funnel-L2 failures that live in rung-L2/L3 scenarios — interaction situations nobody aimed at.)

Eight measured runs of the harness tell one story. Mapping (funnel L1) works — the harness finds ~94% of the product's surfaces. Verification (L3) works — oracles catch what they're pointed at. But aiming (L2) — actually attacking the situations where the bugs live — has been stuck at 9% for four straight runs, under three different philosophies:

  • Hand-authored scenarios (usage-first): real situations, but a run produces ~10 of them, and the author's imagination is the ceiling. The missed bugs sat in situations nobody happened to write.
  • Better scoring (attention formulas): re-rank the candidate list by where the vendor's tests are thin. Failed twice — a score can only reorder a list; it cannot put a missing situation onto the list.
  • More budget: longer runs converged to repetition, not coverage — with no enumerable space, "keep searching" means "keep circling."
The core move

Stop authoring situations and stop scoring guesses. Author a small set of trusted flow atoms, define a small algebra of operators that combine them, and let the machine generate every valid combination as a candidate. A generated scenario is an aim — and because the space of valid combinations is enumerable, what you haven't tried becomes a visible, countable debt instead of a blind spot. Aiming stops being a scoring problem and becomes a coverage obligation.

That last sentence is the entire thesis. Everything else in this document is mechanism.

2Intuition: a grammar, not a library

Toy example 1 — language. Nobody writes a dictionary of every sentence. You learn ~10,000 words and a grammar, and you can produce infinitely many valid sentences — while the grammar mechanically rejects word salad. Flow atoms are the words; operators are the grammar; composition validity is the parser. Ten atoms and twelve operators express more situations than ten thousand hand-written scenarios, and — the part that matters — the set of grammatical sentences of bounded length is enumerable. You can know which ones you haven't said.

"The generator" — a definition, once

Wherever this page says generator, it means deterministic engine code — a script, never an agent: the validator + compiler + materializer pipeline, pure functions with byte-identical output for the same (manifest, policy, seed). No model call exists anywhere in the generation path — that's the lesson of rows 1–8, where an agent was the generator and its imagination was the ceiling. The agent appears only before generation (drafting atoms, gated by critics) and after it (triaging reds). Between those two joints, everything is arithmetic — which is precisely what makes "what wasn't generated" a computable debt instead of a blind spot.

Toy example 2 — property-based testing, one level up. QuickCheck showed that generating inputs from combinators beats hand-picking examples: the generator explores corners no human bothers to write. The compositional harness is the same idea lifted from function inputs to system situations: instead of generating an integer, generate "two workers race on the same queue while a crash lands right after a claim, on Postgres." Same philosophy, same shrinking discipline, bigger objects.

Toy example 3 — chemistry. Atoms are hand-vetted and few; molecules are combinatorial and many. You trust the molecule because you trust the atoms and the bonding rules. This is where the manual effort goes: not into writing hundreds of tests, but into making ~10 atoms genuinely trustworthy (real API calls, real oracles) and the bonding rules genuinely strict (a composition that can't establish its preconditions is never emitted).

Why enumerability is the win

With hand-authoring, "did we test enough?" is unanswerable — the space has no boundary. With a grammar, the compiler can materialize every valid situation up to a bound, mark each one attacked / owed / blocked / parked, and refuse to claim "done" while owed cells remain. Our best runs stopped early saying "my model is exhausted" — that stop row is only honest when exhaustion is computed over an enumerated space, not felt.

3The atoms: small, trusted, heavily annotated

Ontology — three catalogs, one job each

Atoms = flows — same thing, two names: "flow" says what it is (a goal-oriented journey), "atom" says its role in composition (smallest trusted, combinable unit). Resources & Values are not atoms — they're the valence: the typed sites where bonds legally form (race needs a shared Resource; sequence needs an output→input type match). They never compose or run alone; ~8–15 classes per product, two kinds: Resource (provisionable state — queue, database) and Value (data — task, workflow-id). Invariants are the third catalog — falsifiable properties attached to flows, becoming the oracles of every composition that contains them. A scenario is a molecule: flows bonded by operators, legality from the types, judgment from the invariants.

A flow atom is the smallest user-meaningful behavior — a goal, not a subsystem. It is one code file in the product's own language: a function whose typed signature carries most of the declarations, plus a decorator carrying only what no signature can express. There is no sidecar metadata file to drift out of sync — the declarations are the code:

At composition time these are types (the generator matches them statically, nothing runs); at execution time the flow receives instances — worker A and worker B race on the same Queue object, each with different Task payloads. The generator never executes anything: it reads the decorator metadata and signatures via import/AST and extracts a normalized manifest (§6). A YAML-shaped projection of the atom still exists — but as compiled output for human review, generated one-way from the code, never authored. Ten to fifteen atoms cover a product like DBOS; the agent drafts them from docs and code, a critic reviews, the user ratifies.

Bonding rules: why generated ≠ garbage

A composition is emitted only if it type-checks: upstream outputs satisfy downstream inputs; preconditions are establishable; race requires a genuinely shared declared resource; interrupt names a real checkpoint; the invariants stay observable; and a deterministic shrink path exists. Invalid combinations are never emitted to fill a grid — the lattice is sparse by construction. This is the difference between combinatorial coverage and combinatorial explosion.

Why this doesn't explode: the pruning funnel

The space is tiered because the nine dimensions play three roles — and the collapse from billions to thousands happens through five gates, each powered by one specific line of the atoms' declarations:

Below the identity tier: replication dimensions (channel · environment · load) don't multiply everywhere — applicability prunes them (CLI parsing gets no database matrix), and covering arrays handle the rest: every pair of dimension values is guaranteed to co-occur in some scenario, collapsing exponential crossing to near-quadratic (decades of combinatorial-testing data: most interaction bugs are 2–3-factor). Value space inside a cell (seeds, schedules, fault offsets, payloads) is infinite and sampled, never enumerated. Depth escalation keeps granularity honest: start coarse, refine cells where evidence or coupling points — the dial is policy, so tuning it is a cheap experiment. Finally the floors select the mandated ~250–350 for the breadth pass; the rest is ranked frontier.

The punchline — and why under-declaring is dangerous

"The declarations are the pruning function" is literal: each field kills one axis of the explosion (signature → invalid sequences · resources → invalid races · checkpoints → impossible fault placements · invariants → irrelevant mechanisms · typed params → inapplicable states · modalities → unimplemented forms). The flip side is R2's warning in the reference: a missing declaration doesn't just lose information — it silently prunes away real cells, shrinking the space where bugs live. Pruning power and blinding power are the same power, which is why the lint checks declarations against what the code actually touches.

Proof the algebra speaks our language: both real findings are compositions

Finding 1 · gc-strand ● availability (w2)

The bug in one sentence: garbage-collect deletes a completed child workflow that a still-pending parent references — after a crash, the recovered parent waits forever for a child that no longer exists.

interrupt — event: process-crash · checkpoint: before-parent-completes
sequence — first the parent forks and awaits children, then gc runs over them
flow(fork-children-and-await) — parent creates children, awaits their results
flow(garbage-collect) — deletes completed workflows, including the children
Caught by: the liveness invariant the atoms already carry (every workflow eventually reaches a terminal state) — the recovered parent never terminates, so the oracle fires. No one had to anticipate this bug; the invariant plus the composition found it.
Finding 2 · fork-nonexistent ● wrong-error (w1)

The bug in one sentence: forking a workflow id that doesn't exist raises a bare Exception, while every sibling API raises the typed DBOSNonExistentWorkflowError — so callers can't handle it.

with_state — precondition: workflow-id-nonexistent (the misuse persona's binding)
flow(fork-workflow) — fork an existing workflow from a step
Caught by: the error-contract oracle — a flow may only raise its declared, typed errors. The misuse persona exists precisely to run every flow from illegitimate states.

Both findings took days of agent judgment to find by hand. As compositions, each is two operators deep — well inside the generator's mandatory coverage floors (every state-sharing flow pair gets composed; every flow gets a misuse binding). The machine would have emitted both as ordinary coverage debt. That's the retrodiction argument for the whole approach.

Where states come from: negation and prefixes, never imagination

The with_state dimension looks like it needs someone to imagine situations ("what if the id doesn't exist?") — which would reopen the authoring trap. It doesn't: states are generated from two mechanical sources, both reading declarations that already exist.

Source 1 — precondition negation over typed inputs. Every typed reference in a signature (workflow: WorkflowId) gets a fixed, engine-owned misuse library — the same six negations for every reference-shaped type in every product, forever:

  • nonexistent — well-formed id, never created (mint a fresh one)
  • stale — existed, then destroyed (valid id → run the destroy flow → use it)
  • wrong-lifecycle-state — refers to an object in a state the verb doesn't accept (fork a PENDING one? a cancelled one?)
  • foreign — belongs to another tenant/queue (the isolation probe)
  • malformed — not even well-formed
  • reused — where single-use is expected

The misuse floor is then arithmetic: every flow × every typed input × each applicable negation = owed cells. Nobody imagined "nonexistent workflow id" — it's negation #1 applied to a declared type. And the oracle has a differential mode needing zero declarations: feed the same invalid input class to every sibling verb accepting that type and compare the errors — five raise the typed error, one raises bare Exception; the finding is an inconsistency, with the product's own siblings as the oracle. (This page narrates; the binding library + floor is c-misuse, 📖 §6b.)

Source 2 — reachable states are flow prefixes. The subtler states (acknowledged-not-completed, recovery-pending) are the effect-sets left behind by running part of another flow: with_state(A, stale-id) compiles to sequence(create, destroy, A). The state axis mostly collapses back into the composition algebra — reachable states = post-conditions of flow prefixes, enumerated from the same effects declarations.

Residual quality-dependence, ranked small: resource lifecycle enums (usually a literal enum in the product source — extractable, not imagined) · destroy paths existing as flows (the surface-census floor already forces this) · declared error types (extractable; the differential mode works without them). The state dimension felt like the hardest of the nine; declared types + negation + prefixes make it the most mechanical.

5How the search runs on top of the algebra

The loop below is abstract, so each step also carries a live trace (amber) following one concrete cell from birth to verdict — including where the environment gets bound, which the abstract version hides. Environments enter twice: at compile (a coordinate the cell is born with) and at run (the bench materializes it).

1 · compileSparse lattice
Every VALID composition up to the bound becomes a cell: owed / covered / blocked / parked. Environment profiles are declared in the model (agent-drafted: postgres-16, sqlite…) and multiply a cell only where applicable — recovery flows get both database profiles; pure CLI parsing gets none. Same composition + same seed across two profiles = an environment matrix, which also arms a differential oracle. trace · cell #1372 is bornwith_environment( interrupt( race(enqueue, enqueue), crash, after-claim ), postgres-16 ) → state: owed. Its sibling #1373 (same tree, sqlite) is also owed.
2 · gateEligibility
Debt floors decide what MAY run: breadth before depth, controls before attacks, per-cell caps — and environment reachability: a cell whose profile the bench can't provision yet becomes infrastructure debt — never silently covered, restored to the frontier when the capability lands. trace#1372: control exists (one worker, no crash, postgres — green ✓), postgres recipe available → eligible. Sibling #1373: no sqlite recipe yet → blocked, logged as a named infrastructure obligation. (Exactly our real multi-executor block: source-confirmed candidate, execution-blocked, waiting on a platform lever.)
3 · rankAttention
Orders the eligible frontier only — severity of threatened invariants, novelty, vendor-test deficit, coupling. Never a coverage claim; no score can promote an ineligible cell. Ranking is the one component with a failed history, so it carries explicit doctrine — bounded failure, signal decay labels, ranker portfolio with a random control lane, online reweighting, per-run metrics, the two-key ladder rule: 📖 §9. trace#1372 ranks high: shared queue resource (coupling), exactly-once threatened (w4), the vendor's tests never crash inside this window.
4 · runExecute + control
The bench materializes the environment binding: provisions a guest with the profile's services (Postgres via its recipe), hands the flow its ctx with handles bound to that instance, then sweeps bounded seeds/schedules/fault-timings inside the cell. Every run gets the universal oracle plane (liveness · terminal-state · undeclared-error · bounds — zero declarations needed) plus the atoms' declared invariants. traceguest up with postgres-16 · 20 seeds × fault sweep around after-claim · seed 17: the task body executed twice — RED.
5 · reactShrink · neighbors
A red preempts new search: peel the tree to minimal, then mutate one coordinate at a time around the find. The environment is a peel step too — if the red survives on the default profile, the finding is not environment-specific; if it only fires on one profile, that is the finding. tracedrop the race → green (contention essential) · red survives seed minimization → finding crystallized with replay recipe · neighbors enqueued: same crash at after-ack; same race, async modality · #1372 → covered-red; the board's cell flips.
The two-stage rule that encodes the lesson of eight rows: coverage debt decides where the harness is allowed to search; attention only decides which eligible cell runs next. The thing that failed twice (scoring) is demoted to tie-breaker; the thing that was missing (enumerable obligations) becomes the gate. Budget splits across three lanes — coverage, evidence-driven depth, open exploration — and the only honest stops are "budget exhausted" or "zero debt."

Two mechanics deserve a sentence each. Shrinking: because a scenario is a tree, minimization is deterministic — peel operators one at a time until the red disappears; the last tree that still fails is the finding. Concretely, for cell #1372's red at seed 17:

Shrink, step by step — every answer is a fact about the bug

1 · peel with_environment(postgres-16) → run on the default profile → still red ⇒ not environment-specific; binding dropped.
2 · peel interrupt(crash, after-claim) → no crash → green ⇒ the crash is essential; keep it.
3 · collapse race to one worker → green ⇒ contention is essential; keep it.
4 · shrink declared values: task-count 100 → 2, payload 64 KB → 1 KB → still red.
Minimal finding: two workers, two tasks, one crash after claim — with a passing control exactly one peel away, and a replay recipe (tree + seed + fault timing) attached. No judgment anywhere in the walk.

Neighborhoods: a confirmed red generates adjacent candidates by changing exactly one coordinate (same crash, different checkpoint; same race, async modality) — evidence buys depth without erasing breadth obligations.

And one extension the machinery gets nearly for free: resource and performance invariants. The observation stream can carry memory, queue depth, handle counts, and operation counts; the oracle plane then enforces bounds invariants ("memory bounded over N cycles", "the queue drains after the burst", "cost grows linearly up the load ladder"). The deterministic sim is uniquely good at this — virtual time compresses a week-long soak into minutes, with zero flakiness. What stays off the sim: wall-clock latency and throughput numbers — virtual time distorts exactly what a benchmark measures, so real benchmarking runs on the bench's real VMs as a separate lane feeding the same ledger. Correctness first; bounds invariants as the fast-follow; benchmarks when a buyer wants numbers rather than bounds.

6One engine, many languages

Atoms must be written in the product's own language — the access channel is one of the nine search dimensions, and testing a TypeScript SDK through a Python bridge would destroy exactly the realism the method is built on. The architecture that squares this with "one engine" is the LSP / Terraform-provider / Temporal-SDK shape:

  • One engine (language-neutral): compiler, lattice, debt, frontier, shrinker, evidence. It never reads Python or TypeScript — it consumes a normalized atom manifest and emits language-neutral scenario documents.
  • Thin per-language SDKs: a decorator in Python, an annotation in TypeScript, a macro in Rust — each providing atom registration, the ctx interface, and an observation emitter. wio atoms export machine-extracts the manifest from code (import/AST), one-way, so the sync problem never returns.
  • Engine-side oracles: SDKs only emit observations (checkpoint reached, effect recorded, typed error, terminal state, resource counts); oracle evaluation runs once, centrally, over that stream. A new language costs registration + ctx + emitter — never a re-port of the generators or the oracle plane.

What freezes as public contract: the manifest schema + observation/runner protocol — versioned, additive-only, the same family as the evidence envelope. Scope: Python + TypeScript first (covers DBOS's both SDKs — making channel a live differential dimension — plus the local-first/JS world); cross-language compositions (enqueue via TS, recover via Python — a real interop bug class) are protocol-supported but a later cut.

Where this engine sits in the product — the bench/searcher/map layers, who writes what, and the economics — lives in 🏛 The product book, Part II.

8The structural rethink: a skill that experiments instead of rewrites

Here is the uncomfortable diagnosis of the current skill: it is prose doctrine. Its rules live as SKILL.md text; every improvement is a rewrite of that text; and prose has no compiler. The proof already happened: the v0.1.4 rewrite silently dropped v0.1.3's async-parity gate — nobody chose that, the rewrite just didn't carry it, and it cost a measured run to notice. Prose rules don't compose, don't diff meaningfully, and can't be A/B tested. A skill that must find its final form by experiment cannot be made of prose.

Judgment

Today's skill mixes all three in one prose document, so every change risks every rule. Separated, each material changes at its own speed with its own safety: engine by tested PR, policy by versioned swap, judgment by brief. The lab's "lever" stops meaning "edit the doctrine text" and starts meaning "a policy diff or an engine PR" — diffable, attributable, reversible.

The end state, in one paragraph

Users ratify ~a dozen trusted atoms. The engine compiles every valid composition into a sparse lattice with explicit debt, gates search by coverage, ranks by a versioned policy, runs through wio, shrinks reds along the tree, and publishes stamped evidence. The agent spends its intelligence only where judgment lives: drafting the model, hypothesizing couplings, triaging reds. Improving the product means: a policy diff or an engine PR, evaluated up the ladder, promoted only when a blind row confirms — while every user's repo, and every claim on their status page, carries forward untouched.

9Why the repo stays stable while the skill churns

The harness is two things in two places: the skill — the searching brain we ship, version, and keep rewriting (four strategies in six weeks: corridors → usage-first → attention → compositional) — and the .workers/ folder — its working state, checked into the user's repository, touched by their teammates. Internally that churn cost nothing; after launch, "we reorganized the taxonomy" would mean asking every customer to refactor files they didn't write. The design has to make that impossible, and it does so with four old principles, applied:

  • Source vs. build output. A compiler changes its optimizer every release and nobody migrates .o files — machine-owned things get regenerated, never hand-migrated. Most of .workers/ (coverage tables, scenarios, bookkeeping) is build output of the skill: delete and rebuild every release, so churn is free wherever the machine owns the file.
  • Interface vs. implementation. pytest froze one tiny interface (test_* functions) and rewrote everything behind it for fifteen years. Our frozen surface contains only facts about the user's product (what it promises, what a queue means) — those change when their product changes, never when our strategy does. Everything encoding how we search stays behind the interface.
  • Code over declaration. A workload written as code is validated by execution against the product's real API — the thing its vendor already keeps stable. Frontmatter and folder placement are validated only by convention — "whatever our current reader expects" — and silently rot on every rewrite. So: prefer code; whatever must be declared is a versioned, additive-only schema; address by key, never by path.
  • Migration is a command. When the declared surface must genuinely grow, wio migrate replays small reviewed changes (Django's move) — and our unfair advantage is that the agent drafted the files in the first place, so it re-derives the new field and the user's unit of work stays constant forever: read a short diff and say yes or no. Never author, never refactor.

The consequences of these principles — the three concrete zones, the change-kinds table, the ledger/balance model of coverage, and the pre-launch rehearsal (one full strategy overhaul must leave the user-ratified zone with a zero diff) — are product behavior now, specified in 🏛 Part II.

10The openness posture: language public, search private

The operators and composition are the key idea — so what ships open, without giving the search away? The resolution is to split what currently travels together. The language must be public: users hold pinned scenario docs in their repos, and a composition tree is only legible if the operator semantics are published — hiding the language would make their own artifacts gibberish. Publishing it costs little: the twelve operators leak from any corpus of scenario docs regardless, and the validity rules are derivable from the semantics (anyone who understands race can infer it needs a shared resource). The search stays private: applicability inference, the floors, the ranker portfolio and its learned weights, sweep planning, fault models — everything eight rows of lab spend actually taught. Ship the verifier, keep the generator: the SQL-public / query-planner-private shape. Chess rules vs. chess engine. The strongest precedent is SQLite itself: the database is public domain, but TH3 — the proprietary harness that drives it to aviation-grade coverage and makes it trustworthy — has been closed and commercial since 2008. The code is open; the testing machinery that produces the trust is the business.

Trust survives the hidden generator on three rails: every claim on a board is backed by a readable, replayable pinned doc in the public language; the validator ships compiled inside the CLI, so "valid" is independently checkable offline against the public spec; and the explain endpoint makes coverage claims falsifiable — any skeptic can probe any situation they care about and catch a lie at any point of the space. The extraction risk of that endpoint is bounded by design: answers carry state + citation, never mechanism; probing is per-project, budgeted, and audited; and a maximal extraction reconstructs only the enumerator — the publishable-paper layer — while the tuned search never passes through the endpoint at all.

And the no-ratifier argument, from the same posture: ratification (F2) assumed a user who knows their product's truth. In our own fleet lanes there is no such person — the maintainer is the only true ratifier, reachable only through filed issues. So fleet lanes run self-ratified: critic gates substitute for the human, judgment-holds queue without blocking, and maintainer responses become the ground-truth channel (a closed-as-intended is model-correction feedback, not a loss). The measurable cost — false reds that die at triage — is exactly the M2 evidence we want in hand before any customer runs user-ratified mode. The binding rules for both modes live in 🏛 Part I.

Prior art — SQLite (added 2026-07-16, from a talk by its creator)

SQLite arrived at three of this design’s moves twenty years early, at a lower grain. (1) Enumerated fault sites as a breadth floor: sqlite3FaultSim(n) plus malloc/VFS shims mark every point a dependency can fail, and the harness loops until every site has fired and the system survived or failed clean — visit-all-of-an-enumerated-space, our Stage-A floors at the fault-site grain (and the lineage behind FoundationDB/TigerBeetle/Antithesis-style simulation, and our own DST substrate). (2) A coverage criterion on the judge: TH3 drives the core to 100% MC/DC — every boolean sub-condition proven to independently flip its branch (DO-178B flight-software grade). Hipp’s report: at 100%, whole bug classes stopped arriving and refactoring became fearless. Our toybox is the same criterion aimed at the oracle plane — one planted flag per operator × oracle-family, every detector proven to independently flip a verdict. (3) The openness split described above. Lesson held: these disciplines eliminate bug classes only when held at 100% — which is why floors are contracts, not aspirations.

Five questions. Click an answer to see the reasoning.

Question 1
Why can compositional generation move the aiming needle when two attention formulas could not?
The attention formulas failed structurally: they ranked candidates that already existed, and the missed bugs sat in situations that were never on the list at all. Generation attacks exactly that — the algebra materializes every valid situation up to a bound, so "never tried" becomes countable debt that gates the search. Speed and shrinking are real benefits but not the mechanism; operators don't encode vendor deficit (that stays in ranking).
Question 2
Which atom declaration is what makes race(A, B) a legal composition?
Races search contention, and contention needs something contended — the bonding rule requires a shared declared resource (queue, executor-ownership, a database table). Outputs→inputs is sequence's rule; checkpoints belong to interrupt; modality is an independent binding dimension. This is also how the generator finds coupled flow pairs for interaction search: shared resources are statically countable.
Question 3
A generated scenario goes red. What makes its minimization deterministic rather than a fresh search?
Structure is what buys determinism: drop the environment binding, drop the interrupt, collapse the race, reduce declared shrink inputs — each step either keeps the red (continue) or loses it (that piece was essential). The pinned seed makes each step reproducible but doesn't tell you what to remove; the control tells you the simple case works but the attack may differ in several coordinates at once; oracles don't map to operators.
Question 4
Under the engine / policy / judgment split, what does a typical search-improvement experiment become?
Most search-behavior changes (floors, weights, budgets, caps, bounds) are policy — data, not code — so an experiment is a policy diff against a fixed engine, and the ladder kills weak ideas for cents before the one expensive rung. Prose rewrites are the failure mode this design retires; engine PRs are for new mechanisms (rarer); fleet findings are not a measurement instrument — the blinded lab is.
Question 5
What did the row-8 regression teach that the migration path enforces structurally?
Row 8 stacked the attention thesis and the aim-debt gate; it regressed, and no one could say which lever hurt (or whether one helped). The evaluation plan hard-codes the lesson: taxonomy, then generation with unchanged ranking, then the frontier — one treatment per measurement, with retrodiction decomposing attribution cheaply between rows.
