1The language at a glance

-- a scenario is bindings wrapped around one structure; structure depth ≤ 3
scenario   := binding* structure

structure  := flow(KEY)
            | sequence(structure, structure+)     -- B after A, outputs feed inputs
            | parallel(structure, structure)      -- overlap, compatible flows
            | race(structure, structure+)         -- contend on a SHARED Resource
            | repeat(structure, N)                -- N times, same actor
            | interrupt(structure, EVENT, CHECKPOINT)  -- world event at a declared point

binding    := with_actors(TOPOLOGY)   | with_channel(CHANNEL)
            | with_modality(MODALITY) | with_state(STATE)
            | with_load(PROFILE)      | with_environment(PROFILE)

Six structural/adversarial operators build the tree; six binding operators pin its coordinates. Terminals are always flows (atoms). The generator (a script, never an agent) enumerates only trees whose every node validates.

Why depth ≤ 3 — and why that is not "hundreds of users left to chance"

Depth caps distinct flow types per designed scenario, not actors — "hundreds of users" is the with_load dimension (geometric ladder to 1,000 workers), fully in the space. The 2–3 bound rests on the strongest empirical base rate in testing (NIST combinatorial studies: ~70–95% of field failures are 2-factor, ~99% by 4–6; high-order failures usually shrink to a low-order core — both our real findings are 2-operator). The tail is covered non-silently: emergent high-order interleaving inside load/soak cells (designed depth ≠ experienced depth) · the 15% open-exploration lane (budgeted randomness, starvation-checked) · depth escalation on evidence · and the bound itself is policy — raising it for one coupled subspace is a ladder-cheap experiment.

Anatomy — every operator lives four lives

1 · node schema (a dataclass in the tree — pure data, what the scenario doc serializes) → 2 · validity predicate (static check against the manifest; the bonding rules) → 3 · lowering rule (how it becomes the flat actor-plan the runner executes — runners never see operators) → 4 · peel rule (how the shrinker removes it). One class per operator, ~40–80 lines, all four testable in isolation. All twelve live in engine/operators.py in the harness extension — never in the model, the SDK, or the skill. The catalog is closed: #13 requires logged run evidence + an engine PR (📜 item 03).

Faults: two lowering shapes, and the registry that prices the bench roadmap

Two shapes, because the bench has two. POINT events (process-crash · service-restart-window · client-abandons) lower through interrupt(A, event, checkpoint) — armed at a checkpoint/I/O boundary. AMBIENT fault profiles (latency distribution · partition windows · bandwidth caps · packet drop/reorder) are seed-planned over a whole run, so they lower through a NEW binding with_faults(profile) — the profile's canonical config hash joins the cell coordinate, the network seed joins the sweep. This matches the bench's existing contract verbatim ("user config defines the space; a restore-time seed samples the concrete plan; replay fails closed") — we only name the profile as a coordinate.

The event registry carries capability status, and planned faults are blocked cells TODAY. Each event maps to a bench capability with a status: green (crash/kill·restart EXP-077·latency/partition EXP-056-057·seeded scheduling EXP-089-099), pending (per-packet drop/reorder, EXP-057 remainder), planned (disk faults EXP-058-060·mocked external deps EXP-064). client-abandons is harness-side — no bench work, free everywhere. The compiler enumerates planned-fault cells NOW and marks them blocked with the EXP number as the named infrastructure obligation — so the coverage ledger and the bench roadmap become one accounting: the day EXP-058 lands, its cells flip blocked→owed with no model change. In reverse, the debt ledger PRICES each pending EXP by the severity-weighted cell mass it unblocks ("EXP-058 unblocks Σw 61, mostly durability") — the harness tells the bench team what to build next. (Turso census: ~⅓ of harm-weight is WAL/checkpoint/disk-lifecycle — exactly the EXP-058-060 territory.)

3The atom-authoring rules

@flow(
    key="enqueue-and-complete",                 # R1: kebab-case, unique, addressed by key never path
    resources=(QUEUE_STATE, EXECUTOR_OWNERSHIP), # R2: EVERY shared state touched — under-declaring hides
                                                 #     couplings from race(); lint checks vs code reads/writes.
                                                 #     R2b: declare at the ROW-CLASS grain (workflow-rows,
                                                 #     queue-entries), NEVER "the database" — coarse grains make
                                                 #     everything couple with everything, inflating the lattice
                                                 #     AND destroying the coupling prior. Granularity is the dial
                                                 #     that decides whether gate 1 prunes 350× or not at all
    invariants=(EXACTLY_ONCE, ACK_NOT_LOST),     # R3: ≥1; falsifiable; ratified as text by the user
    modalities=("sync", "async"),                # R4: only forms the code actually implements
)
def enqueue_and_complete(ctx, queue: Queue, task: Task) -> Result:
    # R5: inputs = typed params (Resource/Value classes only); outputs = return annotation
    wf = ctx.client.enqueue(queue, task)
    ctx.checkpoint(AFTER_CLAIM)                  # R6: a checkpoint at EVERY await/state-transition
    return ctx.await_result(wf)                  #     boundary — granularity here decides which fault
                                                 #     windows exist (the gc-strand lesson)
  • R7 — goal, not subsystem: an atom is a user-meaningful journey; "the queue module" is not an atom, "enqueue work and observe completion" is.
  • R8 — no hard-coded coordinates: no actor counts, environments, events, or loads inside the atom unless intrinsic to the goal — those are the generator's dimensions.
  • R9 — cite everything: every invariant and applicability claim carries a doc/code citation (critic-checked).
  • R10 — deterministic body: no wall-clock, no ambient randomness; time and randomness come through ctx.
Reaching INTERNAL state (checkpoint/WAL/MVCC-class bugs) from user-behavior atoms

Internal state is always (external history × timing) — both ours. Four ladders: (1) amplifier configs — an environment profile that tightens internal thresholds (tiny WAL, aggressive GC) so internal transitions fire every few operations; declared, legitimate, vendors do it themselves. (2) Sub-API timing sweeps — the bench controls I/O and scheduling, so every I/O boundary is a fault/abandonment site inside any internal process, no state ever named (crashclock heritage); for pure in-memory races, instruction-granularity preemption (hypervisor: instr-preemption, seed-interleaving). Three checkpoint grains: atom-declared (semantic) · I/O boundaries (free, sweepable) · instruction preemption (heavy artillery). (3) SUT-side markers — opt-in: matched product log/trace lines join the observation stream as fault-arming checkpoints. (4) Probe atoms — operator-persona flows (integrity_check, close-reopen-read) sequenced after adversity turn the product's own checkers into oracles. Never manipulated: internal state directly — a state reachable only by teleport isn't a bug users can hit; if it's reachable, some history×timing produces it.

class Queue(Resource):                      # provisionable, stateful, contended-on
    def provision(ctx) -> "Queue": ...       # create one when no upstream flow provides it
    def teardown(ctx, q): ...                # cleanup; enables repeat() re-establishment
    # identity matters: race() binds children to the SAME instance

class Task(Value):                          # data: produced, consumed, generated
    @staticmethod

Rule of thumb: Resource if the product holds state about it between calls (queue, database, subscription); Value if it's data that moves through calls (task, id, payload). Both are the type vocabulary sequence/race match on; ~8–15 per product, all in model/resources.py.

6aWithin-cell search: seeds are not blind sampling

The lattice aims at a situation; the within-cell search finds the values and timing that trigger the bug inside that aimed situation. Random sequential seeds would be a weak way to do this — so three of the four sub-dimensions are searched smartly, not sampled:

Sub-dimensionMethodGuarantee
fault timingexhaustive sweep over declared checkpoints + I/O boundaries (a finite set)covered — not a gamble
interleavingpartial-order reduction (distinct schedules only) + PCT depth bounds — systematic, not random seedsbounded for shallow (most bugs); a computable probability curve for deep
data valuesboundary-biased Arbitrary generators + coverage-guided selection (the AFL/Antithesis move: next seed maximizes new coverage)probability mass concentrated on edges, not uniform over infinity
rare-value × deep-schedulethe genuine residual — budgeted seeds, escalated on near-miss evidencenone — conceded (the thesis's "rare values / deep sequences" tail)

Honesty rules: a cell records "attacked with N seeds," never "proven safe" — green-with-a-seed-budget, budget visible as a policy dial. Depth escalation multiplies a cell's seed budget on a near-miss/divergence (bounded, decaying) — the unbounded budget is spent reactively on signals, not uniformly on hope. Going deep is cheap where it matters: seeds in a hot cell share the build key (~¼s restore), so 1,000 seeds in one suspicious cell is minutes. Two distinct seeds per run — scheduler seed (interleaving) and network/fault seed (ambient plan) — stamped separately so shrink can hold one fixed while varying the other. The seed cannot guarantee finding a rare bug; nothing can. What changed vs rows 1–8: seeds now fire inside an aimed cell, timing is exhaustive, interleavings are systematic, values are biased+guided — so the residual gamble is confined to one dimension, budgeted, and logged as debt rather than hidden as green.

8Engine internals: the three loops, and where a doc's fields come from

The engine iterates the space in three nested loops, in three places, with three termination guarantees:

# LOOP 1 — enumerate (compiler; milliseconds; the ONLY loop that visits the ENTIRE space)
def compile(manifest, policy):
    for tree in valid_compositions(manifest, policy.bounds):   # typed walk, depth ≤ 3
        for coord in applicable_bindings(tree, manifest):      # env × modality × topology × state…
            cells[cell_id(tree, coord)] = classify(...)        # owed/covered/blocked/parked
    return lattice, debt_ledgers                               # always completes; re-runs free

# LOOP 2 — drain (wio harness run; the execution loop over OWED cells)
def run(budget):
    while budget.remaining() and (cell := frontier.next(lattice, evidence)):  # gate, then rank
        doc = materialize(cell, next_seed(cell))
        verdicts = bench.execute(doc)                # → wio; the metered part
        ledger.append(envelopes(verdicts))           # evidence, on disk
        lattice.update(cell, verdicts)               # owed → covered / red / blocked
        if verdicts.red: shrink_and_pause(...)       # reds preempt

# LOOP 3 — sweep (runner, inside one scenario): for seed → for fault-offset → execute
the drain's key property — loop position lives on disk

Loop 2 holds no state of its own: "where we are in the space" IS the lattice + evidence ledger. Kill it mid-loop, run it tomorrow — the frontier recomputes from disk and continues exactly where reality left off. That's why it can be driven by anything (the skill's EXECUTE episodes in budget chunks, cron on main, CI) with no long-lived search process, and why frontier.next() → nothing is the computable "zero debt" that replaced feeling-based stops. Completeness lives in loop 1; progress in loop 2; depth in loop 3.

shrink & neighbors — one mutation operator, two directions

Shrink (inward): on a confirmed red, execute the doc's shrink_plan as delta-debugging — apply the next peel, re-run with the pinned recipe (determinism ⇒ one run answers each question; nondeterministic systems need N statistical reruns per step), still-red keeps the smaller tree, green restores the essential element; then value bisection along declared shrink dimensions. Cost ≈ plan-steps + log₂(value ranges) ≈ 10–30 runs, same build key. Output: minimal tree · the peel log (each verdict is a fact about the bug: not-env-specific, crash-essential…) · the control (the last green, one peel away) · replay recipe — assembled before any agent looks. Neighbors (outward): mutate the minimal cell's coordinate one axis at a time (next checkpoint · other modality · sibling env · swapped resource-sharing flow · adjacent state). Neighbors are ordinary cells: they receive the §9 rank boost, never a gate exemption; one-coordinate keeps verdicts attributable (the red/green frontier maps the bug's extent, into the finding doc); spread is one evidence-driven hop at a time, so neighborhoods can't explode.

9Stage B: ranking, done well

Ranking is the only component with a failed track record (two attention formulas, both dead), so it gets explicit doctrine. First, its failure is bounded by design: Stage A owns coverage, so the worst ranking is random order with identical final coverage — ranking only decides time-to-first-finding, value captured under a budget cut, and how fast red-neighborhoods open. That bound is the license to learn ranking rather than solve it a priori.

the autopsy both failures share

Signals derived from the past decay — historical issue density concentrates spend on territory the vendor already fixed (the DEC-027 retrodiction REJECT said exactly this), and one frozen formula is a monoculture that starves whole classes. Doctrine: never THE formula; a measured portfolio with decaying memory.

SignalNatureDecay handling
severity of threatened invariant (w4 > w1)intrinsicstable
state-coupling strength (shared row-classes, static)intrinsicstable
cost / reachabilityoperationalstable
vendor-test deficit for the exact situationpresent-tenserecompute per target release
code churn near the surfacespresent-tensefresh by construction
novelty vs completed cellsself-updatingcannot go stale
historical issue densitypast-tensecapped, dated, discounted — the DEC-027 trap
  • Portfolio, not formula: several rankers run round-robin across the budget lanes (severity-first · coupling-first · vendor-deficit-first · novelty-first · random as the control lane) — no monoculture, and the random lane is the always-on baseline every ranker must beat.
  • Online reweighting (the bandit layer): a red/near-miss multiplies its neighborhood's rank (bounded, decaying); hollow-green regions decay. All policy data; the exploration lane is the forced-explore arm.
  • Metrics, per run: time-to-first-confirmed-red · weighted-findings-vs-budget-fraction curve (area under) · retrodiction regret (holdout found at K=20/40 vs perfect order). Rankers compete on a scoreboard, not in arguments.
  • The ladder rule, hard: a candidate ranker ships only after beating random AND the incumbent on retrodiction, on two answer keys (the overfitting guard), one change at a time. Ranking is pure ordering with zero execution — there is never an excuse to test a ranking idea with a row.

Determinism is law here too: ranking is a pure function of (lattice, evidence state, policy, seed) — signals are mechanical counts, weights are frozen policy data, the bandit multipliers are fixed decaying rules, even the random lane is a seeded PRNG. No agent ever touches the ordering — agent influence reaches the queue only through disk (new atoms → recompile; triaged evidence → neighborhood boosts). This isn't hygiene: a ranker must be a pure function to be retrodictable, and retrodictability is what makes the portfolio improvable at all.

One-line doctrine: coverage is guaranteed by floors; ranking is a continuously-audited bet on order, run as a measured portfolio with decaying memory — never a single clever formula.
