The operational reality of the deployment tiers, written down so it stops living in heads. Companions: the devbox layout note (~/work/product/README.md), the interception rules (interception/README.md), and the design set via skills-git/DESIGN-TRUTH.md.

The tiers, as they actually exist

  • dev — Convex dev:courteous-pig-756 · dev-api.workers.io · the metal bench on demand. Deployed by the dev job of .github/workflows/deploy-convex.yml on pushes to the dev branch touching convex/**. This deployment is what the live fleet uses — treat it as integration, never a scratchpad.
  • prod — Convex prod (GitHub environment convex-prod, separate deploy key) via main push or manual dispatch; public CLI binaries via release-please (release-cli.yml, publish-cli.yml).
  • quality gates — PR CI (quality.yml, rust-quality.yml), nightly determinism regression (dst-nightly.yml), and the metal AMI pipeline (bake-host-ami.yml: main pushes touching hypervisor paths → bake → two-guest smoke gates → AMI refresh; gate evidence preserved on failure per PR #134). Rollout of baked AMIs is the deliberate operator step described in docs/hypervisor/fleet-rollout.html.

How a client picks its world

A wio environment is nothing but binary + four env vars + a config dir: XDG_CONFIG_HOME (isolated auth/session state), WIO_CONVEX_URL, WIO_API_URL, WIO_WORKOS_CLIENT_ID (resolution in packages/wio/src/config.rs). Named profiles on the devbox:

  • ~/bin/wio — the fleet: staging-worktree binary + dev api/convex + ~/.config/wio-staging. Untouched until the retirement checklist in the staging worktree's DO-NOT-REMOVE.md completes (PR #126 was superseded by #125, so a main-built binary is expected equivalent; rebuild → repoint → verify one lane → remove worktree).
  • just wio-dev (interception/justfile) — the binary from the current branch + dev api/convex + ~/.config/wio-dev.
  • personal Convex — only when a task edits convex/: npx convex dev (personal deployment) or npx convex deploy --preview-create <task> (ephemeral); point WIO_CONVEX_URL at it.

Rules: the shared dev deployment changes only via dev-branch pushes · experiments get their own deployment · prod only via main.

Per-task isolation

A dev task = its own checkout + its own deployment + its own config dir, all disposable. Direction (2026-07-16): sandbox-per-task — a container from one baked dev image (warm build layers, cgroup limits); scaling out runs the same image on more machines; the endpoint is the bench itself as the sandbox provider. Git worktrees are the explicitly-interim mechanism.

Metal hosts attach by enrollment, not assignment

The CLI has no hosts verb and never assigns hosts. The baked AMI carries the host service (ready only after kldload + SMT parking + metal preflight, packages/hypervisor/ops/host/launch.sh); agentd connects outward and enrolls with whichever deployment its host-side config points at (convex/platformHost.ts: enroll, claim, report, renew), appearing there as capacity. Re-aiming a host at a different deployment is a host-side config change + service restart. Clients just create work; dispatch places it (convex/platformOps.ts, workloadDispatch.ts).

Metal admission — the two tracks

Track 1, local: all iteration — the interception engine, its eval suites (retrodiction is zero-execution; oracle work replays recorded streams), the toybox, drafting, shrinking, the smoke, every sim-reachable cell. Track 2, metal: metal-only cells accumulate as a queue; the frontier emits a batch manifest (frozen scenario docs · build keys · estimated runs/wall-clock/cost · debt paid); the operator approves the number; the host is started, drained, stopped (idle-watchdog backstop). Metal never idles and never hosts exploration. Sim-vs-metal divergence on the same doc+seed is itself signal (the ND class; the M14 simulator-oracle comparison).

Interception's lane

Part 5 of the product (interception/): local monolith for engine and evals (no service in the search loop, by design) → the dev deployment for bench execution → prod untouched until the platform work un-parks. Interception CI lanes stay separate from the wio release lanes. The generation package is never published in any form; composition is spec-public, source-private (the validator ships compiled inside the wio binary).

Known cleanups

  • Staging-worktree retirement (checklist in its DO-NOT-REMOVE.md).
  • Fleet lanes move to separate machines on pinned released versions — removes the fleet's devbox dependency.
  • Idle-stop watchdog for metal instances (conductor cron; notify-only for debug-keyed instances).
