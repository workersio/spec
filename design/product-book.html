2The seven pieces

PIECE 1The atom SDKpip / npm · ~700 LOC per language · Python + TS

Responsibility: let a product's behaviors be written as trusted, machine-readable atoms in the product's own language. The entire public API:

@flow(key="enqueue-and-complete",
      resources=(QUEUE_STATE, EXECUTOR_OWNERSHIP),   # side effects
      invariants=(EXACTLY_ONCE, ACK_NOT_LOST),       # ratified promises
      modalities=("sync", "async", "process-parallel"))
def enqueue_and_complete(ctx, queue: Queue, task: Task) -> Result:
    # inputs/outputs derived from this signature
    wf = ctx.client.enqueue(queue, task)
    ctx.checkpoint(AFTER_CLAIM)      # declaration IS emission
    return ctx.await_result(wf)

class Queue(Resource):  provision(ctx) · teardown(ctx, q)
class Task(Value):      generate(rng) · shrink = ["payload_size"]
# ctx: .client (bound handles) · .checkpoint(C) · .observe(event) — the emitter

frozen surface the decorator parameters, ctx, and the two base classes. Changes by: versioned SDK release, additive only.

PIECE 2The enginethe platform's generation service (c-openness) · ~3k LOC + ~3k tests · pure functions

Responsibility: everything mechanical about search. Seven modules, each a deterministic function — no I/O, no model calls, no judgment:

ModuleSignature (conceptually)
extractormodel package → manifest (AST/import pass; flows never execute)
validatorcomposition tree → ok | rejection-with-reason (the 12 operators' bonding rules)
compilermanifest × policy → sparse lattice: cells with states + the 12 debt ledgers; includes the engine-owned misuse negation library (state = precondition negation or flow prefix)
frontierlattice × evidence → eligible set (Stage A: debt gates), ranked (Stage B: attention as tie-break)
materializercell × seed → scenario doc (tree + bindings + auto-peeled control + shrink plan + stamps)
shrinkerred tree × re-run verdicts → minimal finding (peel operators, then declared value shrinks)
oracle planeobservation stream → verdicts, in two tiers: the universal plane runs on EVERY scenario with zero declarations — liveness horizon · terminal-state legality · undeclared-error (incl. the differential sibling mode) · resource bounds — because it checks properties of the stream itself; declared bindings (the ten invariant families) sharpen it per flow. The universal tier is the safety net: it fires even where an atom author declared nothing — gc-strand's hang is caught by it regardless of the atom's invariant list

Everything is deterministic from (manifest, policy, seed) — same inputs, byte-identical outputs, forever. Where it runs (c-openness below — language public, search private): the validator ships open (with the language spec — anyone can check any composition); the compiler, frontier, materializer, sweep planner, and oracle evaluation run service-side and never ship. Generation determinism stays an internal lab invariant; only replay determinism is contractual. frozen surface none — the engine changes freely by service deploy; its outputs' formats are what freeze (§3).

PIECE 3The policyone versioned file, lives with the generation service · data, not code

Responsibility: every tunable of search, in one place, frozen ex ante per run: breadth floors · budget lanes (60/25/15) · per-cell depth caps · ranking weights · operator bounds (nesting ≤3) · load ladders · safety rails. An experiment = a diff to this file — two policies race on the same engine; the lab promotes winners. Users run the service default; power users may pin exposed overrides (their overrides are green-zone, additive-schema like everything else) — the live policy file itself never ships (c-openness).

PIECE 4The CLI: platform + harness extensiontwo release trains · one front door

Two layers, deliberately separate (the kubectl/helm, docker/compose pattern): wio proper is the platform substrate — generic, stable, anyone-can-run-anything on the bench, no atoms required, carries auth/metering. The harness client is a separately-versioned, open front-end (Python-first) that dispatches through the same front door as wio harness <verb> — it carries the language surface (SDK integration, extractor, validator, replay client) and fronts pieces 2 + 3, which run as the platform's metered generation service (c-openness below: language public, search private) and iterate weekly through the lab without ever shipping a client release. The boundary between them is exactly the frozen formats: the client posts a manifest; the service returns scenario docs + debt summaries; wio hands back observations and evidence. wio never learns what an atom is; the harness never talks to a host directly.

PIECE 5The skill (plugin)skills repo → marketplace · v0.2.0 first public · thin by design

Responsibility: the judgment the loop cannot mechanize. Its SKILL.md is one operating loop:

  1. uncrystallized red? → reproduce, shrink (wio does the mechanics), triage, write the finding
  2. model stale/thin/contradicted? → re-draft atoms/resources/invariants from docs+code, with citations → critic review → user digest
  3. otherwise → wio compile, read the debt report, wio run the frontier, record friction
  4. stop when the engine says zero-debt or budget — never on a feeling

Plus its subagents: the drafting critic, the park refuter, the red triager. What it no longer contains (the v2→v3 diet): floors, weights, gates, stop rules, scenario formats — all of that moved into pieces 2–3 where a rewrite can't drop them. The skill text can be rewritten wholesale and the search behaves identically; only judgment quality changes.

PIECE 7The platformformal: convex/ + apps/web + environment · hosted, metered

Five services: the bench (managed hosts + the deterministic sim + fault injection + environment recipes + guest snapshots — where wio run executes); the generation service (pieces 2 + 3 hosted: compile · frontier · materialize · sweep-plan · oracle-eval, metered — c-openness); the evidence service (append-only store of envelope records; the only durable harness-written truth in Convex — everything else is a rebuildable projection); the read pages (rebuildable projections over evidence — each a GROUP BY, team-scoped by origin ref, personal otherwise; page design parked, §8) plus the explain endpoint (per-project scope, probe-budgeted, fully audited — c-openness); the GitHub check (posts wio verdict on every PR — the adoption wedge).

Build amortization (the bench's scheduling contract): every run carries a build key = hash(target SHA · build-affecting environment fields · SDK versions). Builds are content-addressed and cached — built once, ever; guests pool warm per (build key, environment) with snapshot restore between runs. The engine's frontier stays the authority on what runs (ranked budget-chunk windows); within a window the dispatcher bins runs by build key to amortize builds — order across windows is ranked, order inside is efficiency-optimized, coverage untouched. Everything in the search space except environment (and channel's SDK runtime) shares one build: a 10–20k-run breadth pass is 1–3 builds, not thousands. Environment profiles carry a build-affecting flag (service swaps share a build; compilation flags don't). And CI verdicts accept the customer's own build artifact — their CI just built that SHA anyway; rebuilding would make the build dominate a seconds-long replay. That artifact reference rides the verdict request in the wire contract.

3The skill: the judgment layer, structured

Piece 5 in detail — how atoms get drafted, scenarios generated, runs executed, and results returned with the agent never holding anything load-bearing in its head. (Folded from the skill whiteboard, 2026-07-16.)

The one design law

Everything below follows from a single rule, bought with the scars of eight rows:

the law

The skill decides nothing a function could decide, and remembers nothing a file could remember. Every episode starts by reading state from disk and ends by writing artifacts to disk. The engine's --json outputs are the agent's senses; the model package and evidence ledger are its memory; conversation context is a scratchpad that can vanish at any moment (compaction, crash, session end) with zero loss.

Concretely, this kills the three historical failure modes: prose rules silently dropped in rewrites (now: gates are engine functions), the agent's stop-feeling ("model exhausted") ending runs early (now: only zero-debt | budget stops, computed), and steering state lost across compaction (now: the dispatcher re-derives everything from disk each episode).

The dispatcher: four episodes, mechanical preconditions

Each wake, SKILL.md runs one pass: call wio harness status --json, match the FIRST true precondition top-to-bottom, run that one episode, write its artifact, end. Priorities are fixed; the agent never chooses between eligible episodes.

1 · RED episodeprecondition: status.uncrystallized_reds > 0
The engine has already reproduced and shrunk (deterministic re-runs — no judgment needed). The skill's job is what remains: classify (product bug / harness bug / infra gap — via the red-triager brief + source reading), write the finding (finding-writer brief: minimized composition, replay recipe, severity, neighbors) and pass the promotion gates (control evidence attached by the engine; red-proof verified; reviewer verdict). Exit artifact: evidence/findings/<key>.md as a draft finding, or a refutation note that reverts the red.
2 · MODEL episodeprecondition: status.model_debt > 0 (orphan surfaces · refuted parks · contradiction flags · stale/failing build spec · first run ever)
The only place deep intelligence is spent. Sub-flows by trigger: initial draft (read docs/exports/code → write atoms + resources + invariants, every claim cited); orphan surface (census floor found a documented API with no flow → draft its atom or park with evidence); refuted park (park-refuter killed a park → draft the atom it was hiding); contradiction (a run observed something the model says is impossible → fix the model, version-bump); build spec (build fails at a new SHA, or the target's CI/build files changed → re-draft build.spec.toml from their CI with citations; baseline-green on the bench revalidates it — a spec that can't produce a green baseline is blocked debt, never silently covered; build-affecting classifications default conservative and are critic-checked). Every output passes the atom-critic (false invariants? missing checkpoints? under-declared resources? — lint catches the mechanical cases first) and lands as a digest for ratification. Exit artifact: model diff + digest; officials never run against unratified model changes.
3 · EXECUTE episodeprecondition: status.owed_cells > 0 && status.budget_remaining > 0
One command — wio harness run --budget <chunk> — and the engine does everything: selects eligible cells, materializes scenarios + controls, dispatches to the bench, evaluates oracles, appends evidence, updates cell states. The skill monitors and reacts: a blocked cell → write the named infrastructure obligation (and continue); a near-miss/divergence flag → add a coupling hypothesis to the model queue; harness friction → friction.md. It does NOT pick cells, order work, or interpret greens. Exit artifact: the engine's run report + any obligations/hypotheses filed.
4 · STOP episodeprecondition: status.owed_cells == 0 || status.budget_remaining == 0
Render the honest stop report from engine state (never from feeling): debt paid vs remaining, blocked obligations, findings tally, budget spent. If zero-debt: the loop idles until the model changes or new commits land. Exit artifact: stop report; ntfy/PR-comment as configured.

Review gates & ratification modes (F2 + ex-📜 item 08). The skill drafts everything with citations; the human never authors. Two gates, the lab’s law in product skin: search-space changes auto-apply with a model-version bump (critic-reviewed, journaled); judgment changes — weaken/remove an oracle, park a documented surface, change stop semantics or frozen floors — are HELD. Ratification is a mode: user-ratified (customer repos — the digest gates officials, F2 as drawn in the choreography above); self-ratified (our fleet lanes — no valid human ratifier exists, so the atom-critic gate substitutes, model versions auto-apply on critic pass, and HELD items queue non-blocking to the digest cadence while the loop routes around them). In both modes: an oracle is never weakened silently, and nothing reaches a maintainer without a human send. Maintainer responses are the fleet’s ground-truth channel (a closed-as-intended is model-correction feedback).

The pieces talk through five frozen wire formats — manifest · scenario doc · observation stream · evidence envelope · explain response — versioned and additive-only; they are the real public API, specified in 📖 §12.

4One run through the whole system

  1. Draft: the skill (piece 5) reads the product's docs/code, writes atoms + resources (piece 6 green zone) against the SDK (piece 1); the user ratifies wio digest.
  2. Extract: wio atoms export → manifest (format 1).
  3. Compile: engine (piece 2) × policy (piece 3) → lattice + twelve debt ledgers → amber zone.
  4. Select: frontier gates by debt, ranks by attention → cell #1372 is owed and next.
  5. Materialize: scenario doc (format 2) with auto-peeled control and shrink plan.
  6. Execute: the bench (piece 7) provisions the environment binding, runs atoms in their runtime; the SDK streams observations (format 3); the oracle plane issues verdicts.
  7. React: red → shrinker peels to minimal; neighbors enqueue; evidence envelope (format 4) appends locally and to the platform.
  8. Surface: the board's cell flips; the PR check posts the verdict; a draft finding awaits promotion gates. Repeat from 4 until zero-debt or budget.

5The repos: where the code ends up

Six parts to the product. Parts 1–4 are the unopinionated substrate; part 5 — interception — is the opinionated bug-finding approach this whole book describes, named for its north star rather than its mechanism so the name survives any internal rewrite. Naming rule: "harness" keeps its one existing meaning — the initialized workload setup in a target repo (what wio harness <verb> operates on); the CLI stays in the substrate (someone using only the bench never touches interception) and links the composition crate one-way for offline validation. Environments live in three homes by change-rate: the provisioning capability + generic recipes = substrate (part 2) · environment-as-search-dimension (applicability, build-affecting, blocked cells) = interception · the per-product build.spec.toml = their green zone. Part II — the experience

6The design, concretely: three zones in one folder

Put the four principles together and .workers/ divides into three zones with different ownership and different change rules:

Product truthuser-ratified · frozen interface
A small set of flow atoms: mostly runnable code (how to enqueue a task, how to check it completed) plus a minimal declared block (what this flow promises, which invariants must hold). Facts about their product. Drafted by the agent, ratified by the user. Changes only when the product changes. model/flows/enqueue_and_complete.py  ·  model/resources.py
Search statemachine-owned · regenerable
Everything encoding how we currently search: which situations exist, what's covered, what's owed, generated scenarios, priority views. Compiled by the generation service from the product truth. Deletable and refetchable at any time — so its shape can change with every service deploy, invisibly. generated/scenarios/  ·  generated/coverage/  ·  generated/debt/
Evidenceappend-only · immutable
Confirmed findings and run records, each stamped with the exact model and skill version that produced it. Never regenerated, never migrated — history stays readable under the version that wrote it. evidence/findings/  ·  evidence/runs/
Ownership decides change rules. Green = user's, stable, tiny. Amber = ours, churns freely, regenerated. Grey = history, frozen forever.

A flow atom, to make "mostly code, minimal declaration" tangible — one file, declarations living in the code so nothing can drift (a YAML projection is generated from it for review, never authored; the full anatomy — every field's job, the resource classes, the type-derivation — is ⚗️ §3):

A change to the flow-code interface itself (rare, major version) review a diff Agent rewrites the atoms against the new interface; deprecation window; hard-fail with a clear message rather than silent misreads.

Notice what disappeared from the table: there is no row where the user reorganizes files, renames anything, or authors content. The worst case in the whole design is "read a short diff." And the two amber rows should be rare precisely because Principle 3 keeps the declared surface tiny — most of what we'll want to change lives where changing it costs nothing.

But wait — if the search record is regenerable, how do we know how much we've searched?

This is the sharpest question in the whole design, and it exposes a distinction hidden inside "search state." The amber zone is really two things, and only one of them is regenerable:

  • The map — which situations exist, which are valid, what's owed, what should run next. This is a pure function of the green model plus the skill's current policy (generation is required to be deterministic from model-version + policy + seed). Regenerating it is just re-running a compiler; nothing in it was ever information you could lose.
  • What actually ran — this is never stored in amber as truth. Every run and every finding is appended to the evidence ledger (the grey zone): immutable, each record stamped with its full semantic coordinate (flow, modality, event, seed, fault timing) and the exact model and skill versions that produced it.
The ledger and the balance

"How much have we searched?" is answered by recomputation, never by a stored file: coverage = evidence ledger ⨯ current map. It's a bank account — the ledger is the transactions (grey, append-only), the balance is a derived view (amber). You can delete the balance file any time, because the ledger regenerates it. That is exactly why amber is safe to reshape every release.

The interesting case is a taxonomy change. What happens to coverage:

  1. Old evidence keeps its original coordinates forever — it's immutable and version-stamped.
  2. The new compiler maps old records into new cells wherever the mapping is deterministic; those cells count as covered.
  3. Cells the old slicing never distinguished honestly show as unsearched. That's deliberate, not a loss — the migration rule is "no false explicit coverage." If the new taxonomy splits a situation the old one lumped together, we genuinely don't know both halves were covered; claiming otherwise would be the lie. We re-search them, and deterministic seeds make replaying old scenarios into new cells cheap.

So a taxonomy change never loses what we did (the ledger is untouched) — it can only shrink what we're allowed to claim. And that shrink is precisely the reason we wanted the new taxonomy in the first place.

Who drafts a migration — deterministic code or the agent?

Both, chosen by the kind of change:

  • Mechanical changes → deterministic code. Rename a field, add a field with a constant default, restructure the YAML shape. Literally the Rails/Django pattern: a small versioned script, testable, replaying identically on every repo. No model involved.
  • Semantic changes → the agent drafts, because deterministic code can't. If flows must now declare checkpoints:, no script can know where your product's meaningful checkpoints are. But the agent derived the original flow atoms from the user's docs and code — so it re-derives the new field the same way, and its output is never applied directly: it's a diff the user approves.

Both tiers funnel into the same human motion — review a diff. A change that fits neither tier makes wio migrate hard-fail with a message saying what's needed; it never silently guesses.

How we know the line is drawn right before launch

The boundary is a claim, so it gets a test. Before the schema is declared public: run one full internal search-strategy overhaul — swap the taxonomy, swap the ranking — and check that git diff on the user-ratified zone is empty. If any strategy change forces an edit to a green-zone file, the boundary is in the wrong place and we move it before customers exist, while moving it is still just a branch.

The contract, in one sentence each

Green zone: yours; tiny; mostly code; we address it by key, never by path; its schema only grows, never breaks.
Amber zone: ours; regenerable; its shape is not a promise and may change every release.
Evidence: frozen; every artifact stamped with the versions that made it; always readable.
Migrations: deterministic scripts where mechanical, agent-drafted diffs where semantic, human review in both — never a human that refactors.

7The user flow: who runs what, and when a red counts

Three questions decide the whole user experience: where does search run (and who pays for it), when does a failing workload deserve to be visible, and what does the board show for everything that didn't run. Each has a clean answer once you see one distinction.

Search and replay are different activities with different costs

Search is the agent thinking: reading the product, inventing scenarios, deciding where to aim. It costs tokens and takes hours. Replay is executing a scenario that already exists — pinned seed, pinned schedule, pinned fault timing. It's deterministic, costs only compute, needs no model at all, and takes minutes. A found scenario is a compiled asset: expensive to discover, nearly free to re-run forever. That one fact places everything:

Local, while building
developer's machine · on demand
  • Search tokens — agent drafts new flows & scenarios for the feature
  • Replay no tokens — iterate a draft until control is green and red-proof passes
  • Everything here is draft: visible to you, never on the team board
Continuous, on main
scheduled · budgeted
  • Deep search tokens — the harness keeps hunting new situations against main
  • Promotes scenarios that pass the gates to official
  • Maintains the baseline: last full assessment at a known SHA
CI, on every PR
minutes · gate
  • Replay only no tokens — no searching in CI
  • Impact-selected: re-run official scenarios whose flows touch changed surfaces
  • Verdict = diff vs baseline; everything untouched inherits baseline state
CI never searches — it replays compiled assets against the new commit, which is why it fits in minutes and costs no tokens. The expensive thinking happens locally (scoped to your feature) and continuously on main (budgeted, deep).

Promotion gates (already proven in our own lanes): the control must pass (the simple version of the situation works — so the workload isn't just broken), the red-proof must pass (the oracle demonstrably can fail — so green means something), and a reviewer keeps it. TDD ergonomics: red locally is progress; red on the team board is a promise broken. And "should we allow it?" — yes, always allow running; gate publishing. A tool that refuses to run incomplete things gets abandoned.

Partial runs: what the board shows for everything that didn't run

A PR run replays maybe six scenarios out of hundreds. The board never goes blank for the rest — every cell shows its last official assessment with its age. 10Check your understanding

Six questions, medium difficulty. Click an answer to see the reasoning.

Question 0
A developer is building a workload for a feature that's only half-implemented, and it fails on every local run. What does the rest of the team see on the promise board?
The gate is on publication, not execution: draft runs stay in the developer's workspace, and the board only ever reflects official scenarios. Existing cells are untouched (their last-known state carries forward), and the draft appears at most as an off-board "◐ draft in progress" note — never as a red. Reds earn board visibility only after control-green, red-proof, and review promote the scenario.
Question 1
We ship skill v3.4, which completely replaces how scenarios are prioritized and renames every internal coverage category. What happens in a customer's repo?
Prioritization and search taxonomy are search state — build output. The skill deletes and regenerates that zone on its own; migration and review are reserved for the rare case where the declared user-facing schema grows. (History lives in the evidence zone, not by preserving stale build output.)
Question 2
Why is a flow written as runnable code more durable across skill versions than the same information written as frontmatter metadata?
Execution validates code against something outside our control that is already kept stable — the product's real API. Conventions (field names, folder meanings) are validated only by our own reader, which is exactly the thing we keep changing. Key-addressing is true but applies to both code and metadata; the zone placements in the other options are wrong.
Question 3
A real improvement needs flows to declare something new — say, named checkpoints where faults can be injected. What is the designed path?
The schema is frozen against breaking, not against growing. Additive field + default + agent-drafted values + human review keeps the user's unit of work at "read a diff." Making users author it violates agent-drafts-user-ratifies; reading all formats forever piles up complexity that eventually breaks anyway; and pure runtime inference is right only when it's reliable — when it isn't, the fact belongs in the reviewed declaration.
Question 4
Which change would prove the compatibility boundary was drawn in the wrong place?
The invariant is: search-strategy changes never require edits to user-ratified files. A strategy that reaches into the green zone means strategy concerns leaked into the frozen interface — the boundary must move. The other three are the design working exactly as intended: regenerable build output, immutable stamped evidence, key-over-path addressing.
Question 5
Before declaring the schema public at launch, what is the concrete rehearsal that tests the whole design?
The design's promise is "our churn is never your refactor" — so the rehearsal is to cause the churn on purpose (swap taxonomy, swap ranking) and mechanically check the promise: zero diff in the green zone. Scaffolding, determinism, and hand-authoring tests are all useful, but none of them exercises the one claim the whole boundary exists to make.
